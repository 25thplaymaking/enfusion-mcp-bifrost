# Create a model / prop resource in Workbench

**Goal:** a prefab that is visible and collides in-game — and whose changes are
actually on disk when you finish.

**Needs a human click** for prefab edit mode.

## Two different things are called "create a model"

- **Compiling FBX → `.xob`** — see `import-a-model-from-blender`.
- **Creating a resource (prefab) around it** — this playbook.

## The base prefab carries the collision

Start from **`Props_Base.et`** (non-destructible) or **`Destructible_Props_Base.et`**.
Not using one means manual collision setup, including **enabling `Model Geometry`
on the `RigidBody`** — which is why props built on the wrong base are invisible to
physics while looking fine.

Then:
1. assign the imported `.xob` to **`MeshObject.Object`**
2. set the **`Materials`** array
3. assign a **Layer Preset** to colliders (the FBX `usage` custom property drives
   the physics layers)

**`MeshObject.Object` must point at a real `.xob`** — e.g.
`{D73D5FE0EEFBCD9B}Assets/Props/Industrial/BarrelMetal_01/BarrelMetal_01.xob`. An unset or
invalid path makes the entity **invisible in-game** with no error.

## Persistence — the step everyone forgets

> "Changes to prefabs are permanently stored only after saving the world."

So the loop is: edit prefab → **Apply to prefab** → **Ctrl+S to save the world**.
A `Ctrl+S` inside prefab edit mode saves the *prefab*, not the world, and the world
save is what commits it.

## Sockets and skinned parts

- Sockets are Blender **Empty → Plain Axis**. Name them on the parent
  (`socket_wing_01`) and `snap_*` on the parts — snap points are "extremely
  important" for orientation, because systems such as `SlotManagerComponent`
  consume the empty's position *and* rotation.
- Rig with a Single Bone armature: a `root` bone, then one per movable part, then
  vertex groups + Armature modifier.
- **Bone orientation is not RV-engine style:** animations use the **rotation and
  position of the bone** as the origin, *not* two vertices defining an axis.
- Put modular sub-parts in **their own FBX files** and use `SlotManagerComponent` or
  hierarchy — the old Arma 3 "hide the mesh" approach carries a real performance
  cost.

## Traps

- **Missing game material** → the material name must match **exactly**, hash
  suffix included.
- **"All interaction layers used" error** on a collider → the Layer Preset was
  never assigned, which usually means **Custom Properties were not exported** from
  the FBX.
- **Sockets lost** → forgot **Export Scene Hierarchy**.
- **Skinning lost** → forgot **Export Skinning**, *and* forgot to Reimport.
- **Empty `Colliders` array in Details and empty `Geometry Params` in Import
  Settings** → check the collider prefixes (`UBX_` box, `UTM_` trimesh, …), then
  read the Console Log for convexity/shape errors.
- **Relative material paths are deprecated** — use absolute resource refs.
- **Child variants (wing/lid) need Export Scene Hierarchy only**, not skinning.
- **Texture variants**: make child prefabs and swap the `Materials` array per
  variant. The importer auto-creates `.emat` files (MatPBRBasic, in a `Data/`
  folder) named from the FBX material names; use **Material Assigns** to point
  variants at shared materials.
- **Dynamic props: never use trimesh for collision.** One primitive if possible,
  convex if you need several, wheels as cylinders.
- **`Prefabs/Auto/` is generated by Workbench plugins — never hand-edit it.**
- **Never change a GUID without backing up first.** Same GUID in *different*
  addons means the files overwrite each other; same GUID *within one addon* breaks
  one file.
- **Bold property names** in Object Properties mean "overridden".

## Verify

- [ ] the prefab's base is `Props_Base.et` or `Destructible_Props_Base.et`
- [ ] `MeshObject.Object` resolves to a real `.xob`
- [ ] colliders show a Layer Preset, not "All interaction layers used"
- [ ] **the world was saved** after the last prefab edit
- [ ] visible in a live `wb_play` session, and colliding
